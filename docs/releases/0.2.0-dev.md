# HYPERNOVA 0.2.0-dev

日期：2026-11-16。versionCode `3`，可覆盖安装 0.1.1-dev。仍为开发版，未连接手机或完成真机验收。

## 本次修改

恢复出厂设置：补齐设置搜索结果过滤。已从本机 `assets/index.json` 确认目标为 `factory_reset_key` / `MiuiMasterClear`；在原查询结果与列表刷新处过滤，不清除整个 Settings 数据。云备份、网络重置、其他恢复默认项保留。

新增通知锁定与置顶，按用户最新需求作用于**长按选中的单条通知**：

- “更多设置”左侧增加“锁定”，右侧增加“置顶”。选中后对应文字变为“取消锁定”或“取消置顶”。
- 锁定与置顶各限一条，允许选同一条或不同条；选择新通知会替换该功能的旧目标。
- 使用 Android 通知 key 匹配，不按应用、渠道、标题或分组 key 扩大范围。之后同一应用/渠道发来的其他通知不会自动锁定或置顶。
- 置顶项在 SystemUI 中独立于原分组，再进入最优先排序分区；同类其他通知保留系统分组和排序。取消置顶后重建列表，恢复原生行为。
- 被锁定行不可左右滑动清除。若折叠分组包含该行，限制整组滑动以避免连带清除它；展开后其他行仍按原规则处理。
- 应用对同一 key 的内容更新保留选择；真正移除通知后清理选择，之后重新发布不继承。应用自身撤回通知仍正常。

通知开关为 `notification_item_controls`，默认关闭。选择的两个 key 存在 SystemUI 的模块专用私有偏好中，不保存通知正文。通知功能与流量独立安装；本版继续只需要系统界面和设置作用域。

## 升级与使用

1. 覆盖安装，确认 LSPosed 中 HYPERNOVA 已启用，作用域包含系统界面与设置。
2. 打开模块设置中的“通知锁定与置顶”，重启手机。
3. 长按某一条通知，点击“锁定”或“置顶”；这些选择和取消即时生效，不需再次重启。
4. 验证示例：置顶“LSPosed 已加载”，再安装测试模块使其出现激活提示。管理器通知应单独在最上方，激活提示不继承其锁定/置顶。
5. 如要选择合并组中的某一条，先展开组，再长按目标行。
6. “隐藏恢复出厂入口”保持原开关，升级重启后重新搜索；目标恢复出厂项应消失，云服务/备份结果仍可见。

## 实现与证据

本机 `ShadeListBuilder.groupNotifs` 通过 `StatusBarNotification.isGroup()` 决定分组。模块仅在 SystemUI 进程为选中的 key 返回 false，让原流程将其放入 `ROOT_ENTRY`；取消后恢复真实返回值。没有修改系统服务中的分组元数据或通知内容。

优先分区通过独立的 `PinSectioner` 桥接 DEX 接入原生列表，父加载器为 SystemUI，宿主签名占位类不打包。分组、分区和排序稳定性只对当前及刚取消的目标放行。菜单复用已核验宿主布局及样式。

关键代码在 `feature/notification/` 和 `SettingsSearchHook.java`；反编译定位文件位于 `.local/analysis/systemui/{NotifCollection,ModalWindowView}.java` 及 `com.android.systemui.statusbar.notification.collection.ShadeListBuilder.java`。原始成员通过 `tools/verify-targets.py` 核验。

诊断日志包括：`reset-search INSTALLED/OBSERVED`、`notification-controls INSTALLED`、`notification-lock OBSERVED`、`notification-pin OBSERVED`、`notification-detach OBSERVED` 和 `CHANGED`。命中日志与本地构建不代替真机验收；日志不记录通知 key 或正文。

## 验收范围

本地检查包括单条身份隔离、独立替换/取消、实际移除后清理状态、搜索目标与反向匹配、已有流量边界测试，以及宿主签名、桥接 DEX 打包、Lint、构建和签名校验。

真机尚需验证：原通知菜单及按钮布局、左右手势、LSPosed 管理器与激活提示分离、取消后重新分组、应用更新/撤回、SystemUI 重启、字号/横屏，以及 HyperCeiler 共存。若通知被系统的其他过滤规则隐藏，置顶不绕过该规则，也不会重新发布已消失通知。

恢复出厂设置仍仅隐藏入口；OTA 保持此前确认的客户端范围，当前缺少更新器时显示“不适用”。
